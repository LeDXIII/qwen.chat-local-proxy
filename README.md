# Qwen Local Proxy

**Язык:** Русский | [English](README_EN.md)

Локальный прокси к **chat.qwen.ai** с OpenAI-совместимым API. Транспорт — браузерный: прокси управляет Chrome-профилем (Selenium, профиль `browser_profile/`) и работает через собственный API SPA, поэтому ручная выдача cookies и анти-бот fingerprints не нужны — авторизация выполняется один раз прямо в Chrome прокси.

Ключ API для чата **не нужен**: прокси ездит на вашем собственном залогиненном Chrome.

## Быстрый старт

```
setup.bat   # venv + зависимости + создаёт .env из .env.example
start.bat   # API-сервер на http://127.0.0.1:8000
gui.bat     # GUI чата (работает через тот же сервер)
```

Батники работают из любой папки — каждый сам переключается в каталог проекта.

Первый запрос (или кнопка **«Проверить»** в GUI) поднимает окно Chrome с профилем прокси — залогиньтесь на chat.qwen.ai **один раз**: сессия сохраняется в `browser_profile/` и переживает перезапуски сервера и GUI.

Проверить, что сервер живой и авторизован:

```
curl http://127.0.0.1:8000/v1/health
```

Первый вызов поднимает Chrome и может длиться ~2 минуты; дальше отвечает мгновенно.

## Конфигурация: что и куда класть в `.env`

Файл `.env` лежит **в корне проекта**, рядом с `setup.bat`. Вручную создавать его не нужно: `setup.bat` копирует в `.env` файл `.env.example` при первом запуске, а существующий `.env` **никогда не трогает** — правки после `git pull` сохраняются.

Значения читает `src/config.py` при старте сервера и загружает их в процесс, поэтому GUI и `os.environ` видят их одинаково. Все ключи:

| Ключ в `.env` | Что делает | По умолчанию |
|---|---|---|
| `QWEN_BASE_URL` | Сайт, который автоматизирует браузерный транспорт | `https://chat.qwen.ai` |
| `API_HOST` | Адрес, на котором слушает прокси. Держать `127.0.0.1`: у прокси нет авторизации, `0.0.0.0` или пустая строка откроют его всей локальной сети | `127.0.0.1` |
| `API_PORT` | Порт прокси | `8000` |
| `QWEN_BROWSER_PROFILE` | Chrome-профиль, в котором живёт логин chat.qwen.ai. Относительный путь считается от корня проекта | `./browser_profile` |
| `QWEN_CHROME_PATH` | **Абсолютный путь к `chrome.exe`**, берётся как есть — автопоиска нет. Если Chrome стоит не по дефолту, править эту строку | `C:\Program Files\Google\Chrome\Application\chrome.exe` |
| `QWEN_BROWSER_HEADLESS` | `true` — без окна. Первый логин обязан быть с окном (`false`), и с окном надёжнее работают вложения | `false` |
| `QWEN_BROWSER_LANGUAGE` | Язык браузера, влияет на интерфейс сайта | `ru-RU` |
| `QWEN_PAGE_TIMEOUT` | Секунд на ожидание страницы/SPA | `90` |
| `QWEN_SEND_TIMEOUT` | Секунд на полный ответ (длинный стриминг, чтение файлов) | `300` |
| `DEFAULT_MODELS` | Что отдают `/v1/models` и список GUI, пока живой список сайта не прочитан. Через запятую, id ровно как в пикере сайта | `qwen3.7-plus,qwen3.8-max,qwen3.8-omni-flash` |
| `LOG_LEVEL` | Уровень логов сервера | `INFO` |
| `DEBUG_API` | `true` — сырые запросы/ответы Qwen в консоли | `false` |
| `SPA_HEADER_VERSION` | Версионный заголовок, который сама SPA шлёт на чтения API; транспорт копирует его. Менять только если после обновления сайта чтения начали отказывать | `0.3.16` |
| `DASHSCOPE_API_KEY` | **Опционально**, нужен только для `/v1/images/*` (DashScope — отдельный сервис, к чату отношения не имеет). В `.env.example` закомментирован | — |

Печатать `DASHSCOPE_API_KEY` в `.env.example` не нужно и вредно — в git должен попасть только шаблон с закомментированной строкой.

Прочитать значения, не открывая файл руками:

```
venv\Scripts\python.exe -c "from src import config; print(config.API_PORT, config.QWEN_CHROME_PATH)"
```

**Не коммитьте** `.env` и `browser_profile/`: в профиле лежит живой логин в ваш аккаунт (Windows-шифрованные cookies, привязанные к этой машине), а в `.env` — ваши локальные пути. Оба уже в `.gitignore`.

## API Endpoints

База: `http://127.0.0.1:8000`

| Method | Path | Description |
|--------|------|-------------|
| GET | `/v1/models` | Список моделей (живой с сайта, fallback на `DEFAULT_MODELS`) |
| POST | `/v1/chat/completions` | Чат (OpenAI-формат, SSE streaming) |
| POST | `/v1/chat` | То же, нативный формат `{message, model, chatId, parentId}` |
| GET | `/v1/health` | Статус авторизации/браузера; первый вызов поднимает Chrome, при сбоях отвечает `200 status:"degraded"` |
| POST | `/v1/chat/reset` | Сброс сессии — следующее сообщение начнёт новый чат |
| GET | `/v1/chats` | Список чатов аккаунта |
| GET | `/v1/chats/{id}/messages` | Удалённая история (best-effort; основной источник — локальные `.md`-транскрипты) |
| POST | `/v1/chats/{id}/load` | Сделать чат текущей сессией (parentId восстанавливается из sidecar-файла) |
| POST | `/v1/files/getstsToken`, `/v1/files/upload` | `501` — у браузерного транспорта нет API загрузки; вложения передаются inline в поле `files` запроса |
| POST | `/v1/images/generations` | Генерация изображений через DashScope (нужен `DASHSCOPE_API_KEY`) |
| GET | `/v1/images/models` | Список моделей генерации (тот же ключ) |

Поле ввода генерации картинок из GUI убрано — сами эндпоинты остались и доступны любым HTTP-клиентом.

### Пример запроса

```
curl http://127.0.0.1:8000/v1/chat/completions ^
  -H "Content-Type: application/json" ^
  -d "{\"model\":\"qwen3.8-max\",\"messages\":[{\"role\":\"user\",\"content\":\"Привет\"}],\"stream\":true}"
```

### Параметры продолжения диалога

`POST /v1/chat/completions` принимает:
- `chatId` / `chat_id` — ID чата для продолжения
- `parentId` / `parent_id` — ID предыдущего ответа (response_id)
- `newChat` / `new_chat` — принудительно начать новый чат
- `files` — вложения inline, см. следующий раздел

Последний SSE-чанк перед `[DONE]` — мета `{chatId, parentId}`; сервер всегда отдаёт корректный `chatId`.

### Вложения (файлы в сообщении)

Загрузка файлов у SPA есть только в поле ввода чата, собственного upload-API нет. Поэтому вложения передаются inline в теле запроса, а прокси скармливает их полю ввода тем же drag-and-drop-каналом, которым пользуется сама страница:

```json
{
  "model": "qwen3.8-max",
  "messages": [{"role": "user", "content": "Сколько в сумме? (см. файл)"}],
  "stream": true,
  "files": [
    {"fileName": "total.txt", "fileType": "text/plain", "fileSize": 12,
     "fileData": "<base64 содержимого>"}
  ]
}
```

Сервер распаковывает base64 во временные файлы, прокси кладёт их в поле ввода, **дожидается карточек вложения и только затем печатает и отправляет текст**. Нечитаемый, пустой или слишком большой файл пропускается с подсказкой; если SPA так и не показала карточку — ход уходит текстом с предупреждением (молча пропавший файл хуже, чем заметный). Временные файлы удаляются в `finally` потока.

Лимиты и поведение:

| Что | Значение |
|---|---|
| Размер одного файла | 15 МБ в исходных байтах (base64 раздувает тело запроса примерно в 1.33 раза) |
| Документов на одно сообщение | **5** — ровно столько принимает поле ввода сайта: с шестым `.txt` карточка уже не появляется |
| Картинки | **не** считаются в лимите 5 (замерено: 4 документа + 4 картинки = 8 карточек) |
| Больше 5 документов | `413` с перечислением файлов в `detail` — лучше честный отказ, чем ответ по «первым пяти», о которых вы не договаривались |
| Тип файла | Определяется по `fileType` (MIME), при его отсутствии — по расширению имени |

GUI эти лимиты зеркалит и отказывает ещё до запроса. Кнопка **«Прикрепить»** добавляет по одному файлу за клик — можно нажать несколько раз, список показан рядом с кнопкой. Метод `gui/api_client.upload_file` (POST на 501) сохранён для совместимости, но GUI им больше не пользуется.

### Прогресс хода: SSE-комментарии

Ход с вложениями не мгновенный: файл прилетает в поле ввода, сайт рисует карточку, читает содержимое, потом уходит текст. Чтобы клиент не висел в молчании, сервер шлёт прогресс **SSE-комментариями** — строками с `:`, валидными для протокола и незаметными для обычного парсера OpenAI (SDK их молча игнорирует):

```
: progress Файл total.txt передан в поле ввода (1/2)
: progress Квен прочитал файлы за 6 с
: progress Отправляю сообщение
data: {"choices":[{"delta":{"content":"Всего "}}]}
```

Полный набор фаз: `Открываю страницу...` → `Готовлю поле ввода...` → `Передаю файл N в поле ввода...` → `Файл ... передан в поле ввода (N/M)` → `Сайт читает файлы: занято N из M карточек` → `Квен прочитал файлы за N с` (или отсчёт `Файлы готовы, отправлю через N с`, если карточки встали быстрее нижней границы ожидания) → `Отправляю сообщение` → `Квен ответил за N с, собираю ответ` → `Получено N символов`. Между фазами сервер держит соединение комментариями `: ping`.

Так ход выглядит одинаково и в GUI (эти строки падают в поле **«Системный лог»**), и у любого raw-клиента:

```python
with requests.post(url, json=payload, stream=True, timeout=None) as r:
    for line in r.iter_lines(decode_unicode=True):
        if line.startswith(": progress "):
            print("progress:", line[len(": progress "):])
        elif line.startswith("data: "):
            ...  # чанки ответа
```

### Model Aliases

Актуальные модели: `qwen3.7-plus`, `qwen3.8-max`, `qwen3.8-omni-flash`.

- Короткие: `plus`, `max`, `omni`, `omni-flash`, `27b`
- Legacy → текущие: `qwen-plus`, `qwen-turbo`, `qwen3-plus`, `qwen3.6-plus`, `qwen3.6-27b`, `qwen3.5-plus`, `qwen3.5-27b` → `qwen3.7-plus`; `qwen-max`, `qwen3-max`, `qwen3.6-max`, `qwen3.6-max-preview`, `qwen3.5-max` → `qwen3.8-max`

Неизвестные имена пробрасываются на сайт как есть.

### Сохранение сессии

После каждого завершённого сообщения сервер перезаписывает sidecar `logs/.session-<chat_id>.json` (`chat_id` + последний `parentId`). Поэтому перезапущенный прокси/GUI может продолжить любой чат без повторной передачи истории клиентом.

**Паттерн продолжения диалога:**
1. Первый запрос → сервер создаёт чат, отвечает `{chatId: "A", parentId: "B"}`
2. Второй запрос с `{chatId: "A", parentId: "B"}` → новый `parentId: "C"`
3. Третий запрос с `{chatId: "A", parentId: "C"}` — контекст сохраняется

## GUI (PySide6)

Подписи GUI на русском — это осознанное решение; сервер и его логи пишут по-английски сами себе, GUI показывает их как есть. Окно разбито на зоны: верхняя панель, системная инструкция, вложения, чат + системный лог, поле ввода.

- **Верхняя панель** — список моделей со своей кнопкой ⟳ («Обновить список моделей»), **«Чат:»** со списком чатов, **«Загрузить»** (загрузить выбранный чат и его историю) и ещё одна ⟳, статус связи с прокси (`Подключение...` → `Подключено` / `Отключено`), состояние сессии Qwen в браузерном профиле (`сессия: ?` → `сессия: проверяю...` / `сессия: активна` / `сессия: неактивна` / `сессия: сервер молчит`) и кнопка **«Проверить»** — опрос `/v1/health`. Первый вызов **«Проверить»** поднимает Chrome, ожидание до ~2 минут
- **«Система:»** — необязательная системная инструкция, уходит вместе с каждым сообщением
- **«Файлы:»** и **«Прикрепить»** — выбор файла (по одному за клик, «йдёт со следующим сообщением»), рядом показаны выбранные файлы и счётчик документов `N/5`
- **«Переписка»** — тёмное окно чата с рендером Markdown и репликами «Вы» / «Ассистент»; в шапке справа — **«Скопировать ответ»** (последний ответ) и **«Новый чат»**. У каждого сообщения своя ссылка **«копировать»**. **«Новый чат»** чистит окно, снимает выбранные файлы и начинает новую локальную сессию; sidecar-файлы старых чатов при этом не трогаются — их можно продолжить через **«Загрузить»**
- **«Системный лог»** — отдельное поле под чатом: в него падают все служебные строки (фазы прогресса, предупреждения, ошибки вида `[Ошибка] …`), а в чате остаётся только то, что сказал Квен. Моноширинный шрифт, цвет по типу строки, потолок в 1200 строк, вертикальная прокрутка без горизонтальной (широкие строки переносятся и влазят в окно), в шапке — **«Копировать лог»** и **«Очистить лог»**
- Чат и лог разделены перетаскиваемой перегородкой: лог можно вытянуть на пол-окна или свернуть
- Отправка по **Ctrl+Enter** (кнопкой **«Отправить»** тоже можно)
- Под полем ввода — живая строка хода: `Жду первый токен — N с (холодный старт запускает Chrome, до ~2 мин)`, затем `Думает — последние данные сервера N с назад (всего M с)`, фазы прогресса сервера с общим временем хода, предупреждение «возможно, зависло, проверьте окно Chrome» если пауза длиннее обычного оборота, и `Оборот не удался — ответа нет. Подробности в системном логе ниже`, если ход так и не дал ответа
- В статус-баре — текущие `chatId` и `parentId` (пока чат не выбран — `чат не выбран` / `родитель не выбран`)
- Первая отправка в новый чат медленнее остальных — это холодный старт Chrome, а не ошибка

## Архитектура

```
chat.qwen.ai SPA  ⇄  Chrome-профиль прокси (Selenium, browser_profile/)
                                ⇄  транспорт SPA (перехват fetch через CDP)
                                          ↓
                              qwen_client.py (src/client)
                                          ↓
              routes.py (FastAPI, /v1)  ⇄  GUI (PySide6) / любой OpenAI-клиент
```

## Переносимость на другой ПК

Репозиторий клонируется и запускается одним `setup.bat`. Что нужно знать про перенос:

- **`venv` не переносится.** Он привязан к интерпретатору, которым создан, поэтому `setup.bat` не верит наличию папки, а спрашивает у неё, запускается ли она: мёртвый venv — это внятная подсказка «удалите venv и запустите setup.bat снова», а не тихая установка в глобальный Python
- **`.env` машинно-зависимый** (путь к Chrome, профиль) — потому его и нет в репозитории, он создаётся из `.env.example`
- **`browser_profile/` не переносится** — логин зашифрован Windows и привязан к машине. На каждом новом ПК вход выполняется один раз
- Батники ищут Python сначала в `PATH`, потом через `py -3` — Python, поставленный без галочки «Add to PATH», тоже подойдёт

## Для разработки

Скрипты живут в `scripts/` и запускаются из корня проекта интерпретатором из venv (`venv\Scripts\python.exe scripts\...`). Почти все они поднимают Chrome с профилем прокси, а профиль допускает **только один процесс одновременно**: сервер и проверочный скрипт не должны работать одновременно, порт 8000 должен быть свободен. Каждый скрипт печатает собственный итог (`RESULT:` / `OK` / `ALL PASS`) — ориентироваться надо на него, а не на код возврата cmd (там же `pause` и `findstr` искажают код возврата, а консоль Windows портит кириллицу в выводе: логи читать редактором, не `type`).

GUI-тест офскринный, Chrome не трогает и безопасен при работающем сервере:

```
venv\Scripts\python.exe scripts\test_gui_refresh_offscreen.py   # 72 проверки GUI → «RESULT: ALL PASS»
```

Интеграционные проверки требуют живого сервера (`start.bat`) и реального аккаунта:

```
venv\Scripts\python.exe scripts\test_e2e.py
venv\Scripts\python.exe scripts\test_sequential.py
venv\Scripts\python.exe scripts\test_chats_retry.py
venv\Scripts\python.exe scripts\probe_docs_stream.py six    # 6 документов → ожидаем 413, ответ не начался
venv\Scripts\python.exe scripts\probe_docs_stream.py fat    # один жирный .txt → цифры из файла + фазы прогресса
venv\Scripts\python.exe scripts\probe_docs_stream.py five   # пять документов → все пять контрольных чисел
```

`probe_docs_stream.py` печатает каждую сырую строку SSE-потока: `PROGRESS <текст>` для комментариев прогресса, `comment   : ping` для keep-alive, `token` для дельт ответа, `meta` для мета-чанка и собранный `ANSWER`. Это способ увидеть, как ход выглядит для чужого OpenAI-клиента, не трогая GUI. Остальное в `scripts/` — исторические проверочные скрипты под конкретную правку (DOM вложений, геометрия кнопки отправки, лимиты поля ввода); они не входят в набор регрессионных тестов.
